## 1. О проекте

### Концепция и решаемая задача

Обычные антивирусы часто проверяют программы до их запуска по сигнатурам или содержимому файлов. Однако вредоносный код легко скрыть за шифрованием или упаковщиками, а также запускать атаки через стандартные системные утилиты (например, PowerShell или командную строку).

Поэтому эффективнее анализировать поведение программы уже во время ее работы: какие процессы она запускает, какие файлы создает в системе и что меняет в реестре в первые секунды своей жизни.

**Syscall AI Detector** реализует подход **раннего поведенческого обнаружения**:
1. Перехват низкоуровневых системных событий через ядро Windows (**ETW — Event Tracing for Windows**).
2. Анализ поведения процесса в коротких временных окнах от момента его старта (рубежи **5, 10 и 30 секунд**).
3. Принятие решений с помощью ансамбля моделей градиентного бустинга **XGBoost**, обученных распознавать вредоносные паттерны (модификация автозагрузки, запуск подозрительных шеллов, запись исполняемых файлов в каталоги пользователя).
4. Автоматическое принудительное завершение всего порожденного дерева процессов при подтверждении угрозы.

### Ключевые особенности

- **Каскадная многоступенчатая детекция (Cascade Evaluation)**: процесс проверяется не один раз, а последовательно на рубежах $5с \to 10с \to 30с$. Если на 5 секундах поведение кажется пограничным или процесс еще не проявил себя, он не снимается с контроля, а перепроверяется следующей моделью горизонта.
- **Хантинг деревьев процессов (Process Tree Hunter)**: анализ поведения учитывает не только сам корневой процесс, но и все дочерние процессы, порожденные им (например, `powershell.exe` $\to$ `cmd.exe` $\to$ `certutil.exe`).
- **Строгая защита от Data Leakage**: исключение системных меток, абсолютных путей, PID и артефактов трассировки из пространства признаков модели.
- **Калибровка порогов принятия решений ($T^*$)**: для минимизации ложных тревог (False Positives) пороги рассчитываются по кривой Precision-Recall на основе оптимизации $F_1$-меры под каждый горизонт индивидуально.
- **Отказоустойчивость**: встроенный супервизор (Watchdog) для процесса мониторинга ETW и потоковый tail-инджестинг с автоматической обработкой ротации файлов трасс.
- **Режим симуляции (Mock Mode)**: возможность локального тестирования и отладки алгоритмов на macOS/Linux без прав администратора Windows и без драйвера ETW.

## 2. Архитектура системы

Проект разделен на две логические и независимые фазы:
1. **Офлайн-фаза (Offline)**: подготовка данных, генерация датасета признаков, обучение и калибровка моделей. Выполняется **однократно** перед эксплуатацией (модель не переобучается на лету).
2. **Онлайн-фаза (Online / Real-time)**: боевой сервис мониторинга и реагирования, который загружает уже готовые обученные модели и в реальном времени анализирует процессы ОС.

### Фаза 1. Офлайн: Подготовка данных и обучение моделей

```text
[Сырые ETW-трассы] (data/collected_traces: malware & valid)
        │
        ▼
[build_dataset.py / features.py]
  - Вычисление t_start и корней деревьев
  - Расчет окон горизонтов: 2s, 5s, 10s, 30s
  - Извлечение эталонных поведенческих признаков
  - Предотвращение утечки данных (Data Leakage)
        │
        ▼
[features.parquet] (Табличный датасет)
        │
        ▼
[train.py]
  - Стратифицированное групповое разбиение по сессиям
  - Компенсация дисбаланса классов (scale_pos_weight)
  - Байесовская оптимизация гиперпараметров (Optuna)
  - Калибровка оптимального порога T* по F1
        │
        ▼
[Готовые артефакты в out/models/]
  ├── xgboost_horizon_{5,10,30}s.json        (Веса моделей XGBoost)
  ├── metrics_horizon_{5,10,30}s.json        (Оптимальные пороги T* и отчеты)
  └── reference_features_horizon_{5,10,30}s.json (Схемы эталонных признаков)
```

### Фаза 2. Онлайн: Непрерывный мониторинг и каскадное реагирование

```text

                                    ▼
       ┌─────────────────────────────────────────────────────────┐

       └────────────────────────────┬────────────────────────────┘

                                    ▼

                       │                         │

                       │                         │
                       └────────────┬────────────┘
                                    ▼
                       [AuditLogger (audit.jsonl)]
```

## 3. Компоненты системы

### SyscallMonitor (C# / .NET)
Расположен в каталоге [`SyscallMonitor/`](SyscallMonitor/). Представляет собой высокопроизводительный сервис сбора трассировки ядра Windows на базе библиотеки `Microsoft.Diagnostics.Tracing.TraceEvent`.
- Создает сессию ядра ETW (`SyscallMonitorSession`).
- Перехватывает системные события:
  - **Process**: запуск (`ProcessStart`) и завершение (`ProcessStop`) с сохранением связей `ProcessID` и `ParentProcessID`.
  - **FileIO**: создание, открытие, запись и удаление файлов (`FileIOCreate`, `FileIOWrite`, `FileIORead`).
  - **Registry**: операции с реестром Windows (`RegistryCreate`, `RegistrySetValue`, `RegistryQuery`) с автоматической нормализацией путей (`\\REGISTRY\\MACHINE\\` $\to$ `HKLM\\`).
  - **TcpIp**: сетевые соединения и обмен (`TcpIpConnect`, `TcpIpSend`, `TcpIpRecv`).
- Сериализует нормализованные события в потоковый JSONL-файл (`traces.jsonl`).

### Генерация признаков (`features.py` & `build_dataset.py`)
- [`src/features.py`](src/features.py): ядро извлечения поведенческих признаков процесса. Скрипт рассчитывает **90 эталонных признаков**, описывающих раннюю активность за заданное временное окно (`horizon`):
  - Частотные характеристики системных вызовов и темп (`events_per_sec`, односекундный пик).
  - Метрики дерева процессов: число дочерних процессов, максимальная глубина дерева, скорость ветвления.
  - Поведенческие флаги и счетчики LOLBins (`powershell`, `cmd`, `certutil`, `mshta`, `rundll32`, `cscript` и др.).
  - Файловые операции: доля созданных исполняемых расширений (`.exe`, `.dll`, `.bat`, `.vbs`, `.ps1`), активность в системных каталогах и папках пользователя, энтропия имен файлов.
  - Реестр: создание ключей автозагрузки (persistence), попытки вмешательства в настройки Windows Defender (tampering), доля записей в `HKLM`.
  - Энтропия распределения типов событий.
- [`src/build_dataset.py`](src/build_dataset.py): потоковый парсер файлов сырых трасс (построчное чтение JSONL без загрузки гигабайтных файлов целиком в оперативную память). Обрабатывает каталоги `malware` и `valid`, рассчитывает временные границы окон и сохраняет итоговый табличный датасет [`out/features.parquet`](out/features.parquet).

### Пайплайн обучения (`train.py`)
Скрипт [`src/train.py`](src/train.py) реализует процесс обучения моделей для каждого горизонта:
- **Защита от утечки между сессиями**: стратифицированное групповое разбиение по сессиям трассировки гарантирует, что все процессы из одного файла трассы целиком попадают либо строго в обучающую, либо строго в тестовую выборку. Это исключает переобучение на особенностях конкретного запуска.
- **Борьба с дисбалансом**: соотношение легитимных и вредоносных сэмплов составляет порядка 15:1. В функцию потерь закладывается штрафной коэффициент `scale_pos_weight = N_benign / N_malware`.
- **Оптимизация в Optuna**: поиск лучших гиперпараметров деревьев (`max_depth`, `subsample`, `learning_rate`, `reg_alpha`, `reg_lambda`) по метрикам `f1`, `pr_auc` или `roc_auc`.
- **Калибровка порога $T^*$**: поиск точки на Out-Of-Fold Precision-Recall кривой, дающей максимальное значение $F_1$, что позволяет свести ложные срабатывания (FP) к минимуму.
- Сохранение артефактов в `out/models/` для использования онлайн-оркестратором.

### Онлайн-оркестратор (`src/orchestrator/`)
Модульная система реального времени, запускаемая через [`src/run_orchestrator.py`](src/run_orchestrator.py):
- **`supervisor.py`**: запускает бинарник `SyscallMonitor.exe`, контролирует его работу и в случае сбоя автоматически перезапускает (Watchdog).
- **`ingestion.py`**: асинхронный воркер, читающий `traces.jsonl` в режиме потокового `tail -f` с устойчивостью к битому JSON, частичной записи строк и ротации файлов.
- **`registry.py`**: потокобезопасное in-memory хранилище состояния всех наблюдаемых процессов. Поддерживает события, пришедшие не по порядку (out-of-order), связывает дерево предков и потомков, выполняет очистку устаревших процессов по TTL.
- **`features_adapter.py`**: трансформирует сырые события живого процесса в матрицу эталонных признаков модели, строго выравнивая структуру колонок с эталонной схемой.
- **`inference.py`**: загружает обученные модели XGBoost и калиброванные пороги $T^*$ для каждого горизонта, производит расчет вероятностей.
- **`scheduler.py`**: каскадный планировщик. Периодически (по умолчанию каждые 0.5с) сканирует активные процессы:
  - Возраст $\ge 5.0с$ $\to$ оценка моделью 5с. Если легитимен — процесс продолжает жить.
  - Возраст $\ge 10.0с$ $\to$ перепроверка моделью 10с.
  - Возраст $\ge 30.0с$ $\to$ финальная проверка моделью 30с.
- **`response.py`**: механизм принудительного завершения процессов. На Windows вызывает `taskkill /F /T /PID`, на Unix использует рекурсивный `SIGKILL` через `psutil`.
- **`audit.py`**: потокобезопасный структурированный логер решений в `out/audit.jsonl` с фиксацией вердиктов, вероятностей, списков завершенных PID и топ-факторов детекции.
- **`mock_monitor.py`**: симулятор трасс для автономного тестирования без Windows-драйвера.

## 5. Установка и настройка

### Системные требования
- **ОС для боевого использования**: Windows 7 (SP1) или Windows 10/11 / Windows Server (с правами Администратора для сбора ETW и завершения процессов).
- **ОС для разработки, обучения и тестирования**: Windows, macOS или Linux.
- **Python**: версия 3.10 или выше.
- **.NET SDK** (для компиляции `SyscallMonitor`): .NET SDK 6.0 или 8.0.

### Шаг 1. Клонирование и виртуальное окружение
```bash
git clone https://github.com/bober/syscall-ai-detector.git
cd syscall-ai-detector

python3 -m venv .venv
source .venv/bin/activate   # На Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### Шаг 2. Сборка SyscallMonitor

Сборка монитора зависит от целевой операционной системы:

#### Вариант А: Для Windows 10 / 11 (.NET 8.0)
Если целевая машина работает под управлением современной версии Windows с установленным .NET 8 Runtime:
```powershell
cd SyscallMonitor
dotnet build -c Release
cd ..
```
Исполняемый файл будет доступен по пути: `SyscallMonitor\bin\Release\net8.0\SyscallMonitor.exe`.

#### Вариант Б: Для Windows 7 SP1 (.NET 6.0, Self-contained бинарник)
Windows 7 официально не поддерживается средой .NET 8. Для надежной работы на Windows 7 проект собирается под `.NET 6.0` в виде **автономного (self-contained)** исполняемого файла, включающего в себя все необходимые runtime-компоненты. При этом на саму целевую машину с Windows 7 не потребуется устанавливать .NET:
```powershell
cd SyscallMonitor
dotnet publish -c Release -f net6.0 -r win-x64 --self-contained -p:PublishSingleFile=true
cd ..
```
Полученный автономный бинарник `SyscallMonitor.exe` из каталога `SyscallMonitor\bin\Release\net6.0\win-x64\publish\` переносится на машину с Windows 7 и запускается от имени Администратора.

## 6. Сценарии использования

### Сценарий 1: Сбор сырых трасс
Для ручного запуска сбора системных вызовов в файл `traces.jsonl` (требуются права Администратора):
```powershell
SyscallMonitor\bin\Release\net8.0\SyscallMonitor.exe
```

### Сценарий 2: Построение датасета
Преобразование сырых `.jsonl` файлов из папки `data/collected_traces/` в матрицу признаков:
```bash
python3 src/build_dataset.py \
  --traces-root data/collected_traces \
  --output-dir out
```
Скрипт создаст файл `out/features.parquet`, содержащий векторы эталонных признаков для горизонтов 2, 5, 10 и 30 секунд.

### Сценарий 3: Обучение моделей
Обучение градиентного бустинга с оптимизацией параметров через Optuna и калибровкой порогов:
```bash
# Обучение модели для горизонта 5 секунд (50 итераций Optuna)
python3 src/train.py --horizon 5 --n-trials 50 --metric f1

# Обучение моделей для остальных горизонтов
python3 src/train.py --horizon 10 --n-trials 50 --metric f1
python3 src/train.py --horizon 30 --n-trials 50 --metric f1
```
Финальные модели, метрики и схемы эталонных признаков сохранятся в каталоге `out/models/`.

### Сценарий 4: Боевой запуск онлайн-детектора
Запуск полноценного сервиса защиты на Windows от имени Администратора:
```powershell
python src\run_orchestrator.py `
  --monitor-cmd "SyscallMonitor\bin\Release\net8.0\SyscallMonitor.exe" `
  --horizons 5 10 30
```
- Оркестратор запустит `SyscallMonitor`, начнет читать события в реальном времени и будет последовательно проверять каждый процесс на рубежах 5, 10 и 30 секунд.
- При обнаружении угрозы процесс и его потомки будут немедленно завершены через `taskkill`.
- Запись вердиктов ведется в `out/audit.jsonl`.

### Сценарий 5: Локальное тестирование в Mock-режиме
Для отладки логики оркестратора на macOS, Linux или без прав Администратора доступен режим эмуляции:
```bash
# 1. Запуск со встроенным дроппером (эмулирует вредоносный powershell -> cmd)
python3 src/run_orchestrator.py --mock-mode --bypass-admin-check --horizons 5 10 30

# 2. Запуск с воспроизведением реальной трассы легитимного процесса
python3 src/run_orchestrator.py --mock-mode --bypass-admin-check \
  --mock-trace data/collected_traces/valid/sample.jsonl
```

#### Параметры командной строки оркестратора:
| Параметр | По умолчанию | Описание |
|---|---|---|
| `--horizons` | `5.0 10.0 30.0` | Список рубежей каскадной детекции в секундах |
| `--horizon` | `5.0` | Одиночный горизонт (обратная совместимость) |
| `--threshold` | `None` | Единый порог вероятности (если не задан, используются калиброванные $T^*$ из метрик) |
| `--traces-path` | `traces.jsonl` | Путь к потоковому файлу трассировки |
| `--monitor-cmd` | `None` | Команда для запуска C# монитора |
| `--audit-log` | `out/audit.jsonl` | Путь к структурированному JSONL-файлу аудита |
| `--log-file` | `out/orchestrator.log` | Путь к общему логу работы |
| `--timer-interval` | `0.5` | Частота тика планировщика проверки горизонтов (секунды) |
| `--bypass-admin-check`| `False` | Пропуск проверки прав Администратора / root |
| `--mock-mode` | `False` | Включение генератора/воспроизведения событий |
| `--mock-trace` | `None` | Путь к файлу трассы для воспроизведения в mock-режиме |
| `--mock-speedup` | `1.0` | Множитель скорости воспроизведения mock-трассы |
| `--process-ttl` | `300.0` | Время хранения завершенных процессов в памяти (секунды) |

## 7. Тестирование и качество кода

В репозитории реализован полный набор из **54 автоматических тестов** на базе **pytest**, проверяющих все модули системы от парсинга параметров до сквозной каскадной детекции.

### Запуск тестов
```bash
# Базовый запуск всех тестов
pytest

# Запуск с подробным отчетом о покрытии кода (coverage)
pytest --cov=src.orchestrator --cov-report=term-missing
```

### Статический анализ и линтинг
Кодовая база проходит строгую проверку типов и форматирования:
```bash
# Проверка качества кода линтером Ruff
ruff check src tests

# Проверка форматирования
ruff format --check src tests

# Строгая статическая типизация Mypy
mypy src tests
```

### Автоматизация в CI/CD
В репозитории настроен CI на базе GitHub Actions:
- [`.github/workflows/python-quality.yml`](.github/workflows/python-quality.yml): проверка стиля и линтинг кода через Ruff.
- [`.github/workflows/tests.yml`](.github/workflows/tests.yml): запуск полного набора тестов на платформе Windows Server с генерацией отчета покрытия.
- При отсутствии весов моделей в репозитории тестовые фикстуры ([`conftest.py`](tests/conftest.py)) автоматически создают минимальные синтетические артефакты, гарантируя стабильный прогон в CI без загрузки тяжелых файлов.
